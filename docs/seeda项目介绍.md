# seeda：从一颗种子开始成长的 coding agent

**seeda 是一个能够在项目中独立成长的本地 coding agent：它既能完成编码任务，也能修改自己的实现、验证新版本、请求接替或回退，并将有价值的改进传播到其他项目。**

项目名称来自“播种”的构想。安装 seeda 后，每个项目都可以选择一个初始种系，建立属于自己的 Agent 版本和成长记录。随着工作推进，不同项目中的 seeda 可以沿着各自的需求发展，成熟的实现可以发布为新的种系，选定的功能也可以嫁接到其他项目。

![seeda 的核心概念](assets/seeda-overview.png)

## 为什么做 seeda

编码工作中，Agent 会反复遇到具体限制：某个工具输出不够清楚，某种任务需要额外的操作能力，已有上下文组织方式不适合当前项目。这些问题既影响当前任务，也提供了改进 Agent 自身的机会。

seeda 希望把“发现限制—修改实现—验证效果—采用新版本”变成一条可以执行、追溯和撤回的工作路径。Agent 拥有创建候选、提交版本、执行验证、读取证据和请求接替的接口；外部运行管理负责把这些请求落实为进程与版本操作。

它面向递归自我改进（Recursive Self-Improvement，RSI）：改进后的 Agent 可以继续参与下一轮改进。这里的成长指实现、工具、提示词、Skill 和上下文处理方式的演进，不是模型权重的自动训练，也不保证每一次修改都带来提升。

## 一个项目如何开始成长

假设你在开发一个应用。进入仓库，运行 `seeda seed`，从全局种系库选择起点；随后运行 `seeda`，系统自动启动或复用守护进程，接入终端界面。

你先让它执行普通编码任务：阅读代码、修改文件、运行测试并修复问题。核心循环很直接：接收输入，请求模型，执行工具，把结果送回模型，继续工作直到完成。TUI 展示对话、流式输出和工具状态，同时支持取消、会话切换和主动压缩。

如果任务暴露了 Agent 自身的不足，你可以进一步要求它改进自己的实现。例如：“Bash 失败信息不够清晰，请在候选版本中改善错误展示，并实际验证。”当前主实例 A 创建独立候选 B，在候选目录修改源码、运行检查并保存版本，再让 B 执行针对性任务。

A 读取测试结果、任务产物和执行记录，判断是否接受这次改动。接受后，它通过 management RSI 接口请求 B 接替主实例；失败则保留 A，继续修复或放弃候选。接替发生在请求边界，旧版本和记录保留，必要时可以回退。

这是一种由任务驱动的成长过程。当前没有默认的定时自进化任务；提供了改进机制，也需要具体目标、执行和质量判断。

## 六个概念，各有职责

| 概念 | 在 seeda 中的含义 |
|---|---|
| 种系 Strain | 一份可以命名、选择、运行和传播的完整 Agent 实现版本 |
| 播种 Seed | 选择种系，为一个项目建立初始状态 |
| 成长 Growth | 在同一项目中改进自身实现，通过候选验证持续迭代 |
| 谱系 Lineage | 记录版本来自哪里、如何沿着项目历史发展 |
| 发布 Publish | 将保存的实现版本和标准介绍登记到全局种系库 |
| 嫁接 Graft | 把其他种系中的选定改进适配到当前项目的候选版本 |

**成长发生在一个项目内部；嫁接引入其他项目或种系的改进。** 两者都需要验证，不能把代码发生变化直接当作能力提升。

例如，项目甲的 seeda 改善了工具错误处理，可以发布为带有标准介绍的新种系。新项目乙可以选择这个完整种系作为起点。已经独立成长的项目丙，则可以让自己的 Agent 只嫁接错误处理功能，保留原有能力。

嫁接以 Git 为基础，由 Agent 使用 Bash 查看差异、应用补丁、处理冲突和适配依赖，然后走候选验证与接替流程。平台没有专用的功能导出/导入工具，也不假定不同项目的改进可以直接插入运行。

## 架构为什么这样拆分

seeda 使用 TypeScript，自行实现 Agent 核心、模型接入与工具循环，不依赖 Agent 或模型 SDK。架构分为五部分：

![seeda 的系统架构](assets/seeda-architecture.png)

| 部分 | 负责什么 |
|---|---|
| TUI / CLI | 用户输入、展示、取消与会话控制 |
| Agent 核心 | 模型与工具交互循环、session、上下文管理和 Skill |
| 模型与工具接入 | 原生 HTTP/SSE、Bash，以及 Agent 可调用的 management 接口 |
| 版本与成长管理 | 保存实现、版本来源、验证、判断与切换记录 |
| 守护与运行管理 | 启动、存活检查、任务路由、版本切换和故障恢复 |

前端只负责交互。主实例与候选复用核心，候选使用独立工作目录和验证会话。Agent 可以主动调用 RSI 接口，自身改进不依赖用户手动分别启动多个进程。

守护进程位于被改进的 Agent 之外，负责存活和生命周期。当新版本启动失败或失去响应时，运行管理可以执行恢复与回退。**守护不判断回答质量，也不判断候选是否更优秀。** 这些结论由 Agent 根据任务证据作出；能运行与更好用是两件需要分别验证的事。

## 成长如何被保存

Git 保存 Agent 的实现版本，SQLite 保存版本来源、验证、判断与切换等元数据，JSONL 保存会话与工具记录，输出文件保存相关产物。

默认情况下，每个项目的运行状态位于自己的 `.seeda/runtime/`，不同项目独立保存版本、会话和成长记录。全局种系库负责提供可选择的实现起点，不替代各项目的运行状态。

发布种系时，需要附带简介、改进、适用场景、限制与依赖、验证情况五项标准介绍，方便快速比较与选择。验证介绍是发布者的说明，不等同于平台认证。发布保存的实现，不复制会话、运行数据库或凭据；修改安装源码也不会自动覆盖已有项目的保存版本。

## 从极简内核起步

seeda 初始保留完成任务和演进所需的基本能力：终端与 Bash 使用、模型调用、工具循环、Skill、session、上下文压缩，以及版本与生命周期管理。

内置记忆主要保存 session。复杂的项目知识组织可以通过可选 Skill 使用，是否进一步内化为 Agent 能力，由后续实际需求和改进流程决定。

这使项目可以围绕真实工作逐步增加能力，而不必在起点预先设计一套庞大的插件或记忆平台。

## 当前状态与使用边界

当前已提供 TUI、原生 DeepSeek 接入、Bash、会话管理、上下文压缩、Git/SQLite 版本管理、外部守护、独立候选验证与接替，以及全局种系库、项目播种和 Agent 自主嫁接流程。

项目仍处于早期阶段。主要在 macOS 验证，Linux 有 CI 检查，Windows 尚未验证。需要 Node.js 24.14+、Git 和 npm，目前从源码安装，采用 MIT 许可证。

Bash 使用当前用户权限执行命令；候选独立目录不等同于系统沙箱。模型服务仍需有效凭据和实际支持的模型 ID。自我改进的基础流程可执行，不代表它会自动持续进化，也不代表改进必然成功。

seeda 的目标，是让一个小而可理解的 Agent 在项目里逐步成长，并使成长有证据、有历史、可回退，也有机会被其他项目继续使用。
