# seeda：面向 RSI 的本地 Coding Agent 架构设计

## 1. 目标与设计状态

seeda 是通过 CLI 交互的本地 coding agent。它从最小模型与工具循环起步，在真实工作中发现自身不足，修改自己的实现，通过独立任务验证改进，再由外部管理进程将新版本切换为主智能体。

核心宗旨：**一项目一种子，独立成长，成熟种系可以传播；成长可追溯，更新可撤回，恢复能力独立于被更新的 Agent。**

本文整合用户讨论，定义首版范围与实现依据；当前已实现 Agent 核心、DeepSeek 原生接入、Bash、session 与简单终端驱动，详见 [[docs/Agent核心实现与验证]]；最小 TUI 已接入，见 [[docs/TUI前端实现与验证]]；数据库、守护、版本切换与最小 A/B 接替已实现，使用与证据见 [[docs/版本守护与RSI运行指南]]。本文完成不代表系统已经实现。此前 [[docs/最小CodingAgent蓝本]] 保留作为基础循环调研，本文补充后来确认的版本管理与 A/B 接替要求；若首版范围不同，以本文为准。

### 已确认的方向

- 初始 Agent 极简：CLI、模型调用、Bash、工具调度、Skill、上下文管理与压缩。
- 面向 RSI：Agent 能检查、修改并验证自身实现，不要求所有能力都实现成插件。
- Git 保存实现版本，数据库保存成长过程与运行选择。
- 外部守护进程只负责存活和生命周期；结果质量由智能体评价。
- A 产生 B，B 在独立环境运行验证；A 依据结果请求 B 接替主角色。
- 旧版本保留，能切换、回退和重新唤醒。

### 后续讨论确认的简洁性边界

- 采用小核心与少量统一接口，先不开发通用插件系统。
- 内置记忆只保存 session 的消息、工具调用与结果、压缩摘要及恢复状态。
- Project Memory 通过普通 Skill 按需使用，不作为 Agent 核心的必需依赖。
- 是否将项目记忆能力进一步内化，由未来 Agent 根据实际任务提出修改，通过候选验证再启用；首版不预先实现。

### 本文采用的具体建议

使用 SQLite 管理成长与运行元数据；本地 JSONL 保存会话；单机一个管理进程、一个主 Agent、最多一个候选 Agent。首版只在完整用户请求结束后切换主角色。通信采用本机 Unix socket 连接 CLI 与管理进程、父子进程管道连接管理进程与 Agent；消息用简单 JSON 表达，不引入网络服务框架。

运行语言已由用户确定为 TypeScript，终端前端采用 TUI。核心循环、工具、session 和模型接入自行实现，不引入 Agent SDK；模型通信采用原生 HTTP/SSE，不依赖模型 SDK。具体运行时版本、模型提供商、TUI 渲染库、超时数值和安装路径待实现前确定。本文不新建应用代码或数据库，不在此阶段强行初始化 OpenSpec；代码实现阶段按 [[AGENTS]] 用 OpenSpec 规划。

## 2. 核心理念

### 2.1 可理解、可修改的执行循环

代码、系统提示词、Skill、工具定义和配置均有明确文件来源。关键调用路径短，模块按职责拆分。Agent 能用自身已有的 Bash 能力查看和修改这些文件，不依赖专门的进化语言或通用插件平台。

插件与 Skill 是增加能力的方式；核心循环、上下文策略和工具实现也允许形成新版本。运行进程不在执行期间原地替换核心代码，避免修改影响当前任务的执行语义。

### 2.2 以实际结果判断改进

自我修改并不等于改进。每次成长记录应说明原问题、修改内容、任务结果和比较依据。A 可以通过测试、产物检查和实际执行记录评价 B；仅一句自我评价不构成接替依据。

质量评价按本次改进目标展开，例如解决某类编辑失败，而不承诺一次验证证明整体能力全面提升。评价可能出错，后续智能体可以根据新证据请求回退。

### 2.3 版本、实例与角色分离

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 版本 | 一组可重新启动的实现文件与对应依赖 | Git 提交对应的版本 A、版本 B |
| 实例 | 某个版本的一次运行进程 | A 的主实例、B 的验证实例 |
| 角色 | 实例当前承担的职责 | 主 Agent、候选 Agent、待接替实例 |
| 会话 | 持久化的交互与工具记录 | 用户任务会话、候选验证会话 |

A、B 不是两个永久身份，也不是两个模型名称。B 接替后成为新的主 Agent，随后可以创建 C。A 退出运行，但实现版本和成长记录保留。

### 2.4 小核心与统一接入

只保留工具、模型和管理三类接口。接口是普通函数、类型与本地消息边界，不是必须加载的插件框架。增量 I 实现工具与模型接口；增量 II、III 再按实际管理操作增加管理接口，不预建空壳生命周期系统。

统一接口方便接入和测试，但不自动保证安全，也不永久限制核心可修改。核心变更通过新版本与独立进程验证生效；新增能力优先选择已有工具或 Skill 能承担的最小形式。

### 2.5 生存与质量分工

守护进程判断启动成功、进程退出、心跳失联和控制通道是否响应。它不检查回答质量、不打分、不判断某个新功能是否更好。质量结论和主动质量回退来自 Agent。

管理进程可检查切换请求的来源、目标存在、目标就绪、当前任务结束等操作条件。这些是生命周期正确性要求，不是质量评价。

## 3. 五部分职责与进程架构

| 部分 | 实现职责 | 边界 |
| --- | --- | --- |
| 1. TUI 前端 | 输入、对话与执行状态、取消、版本选择 | 不调用模型或执行工具，不拥有 session |
| 2. Agent 核心 | 循环、session、上下文压缩、规则与 Skill | 与终端布局及进程切换无关 |
| 3. 模型与工具接入 | 原生 HTTP/SSE、工具定义与实际执行；首先只有 Bash | 不规划任务、不拥有会话 |
| 4. 版本与成长管理 | Git、SQLite、版本关系、验证证据与切换记录 | 不评价质量、不直接管理进程 |
| 5. 守护与运行管理 | 启动、存活、路由、切换、回退 | 不判断候选结果更优 |

五部分是普通模块边界，不要求五个包或进程。先实现 2＋3，通过简单终端驱动实测，再接 1；4、5 在后续增量加入。版本与成长管理由守护进程调用，保持单写数据库。

核心提供 run/cancel 并发出文本、工具开始／结束、请求结束／失败事件。TUI 只发送用户动作并订阅事件。A/B 复用同一个核心，不增加第六套引擎。

最终运行路径为 TUI → 守护路由 → 主实例 → 模型与工具，事件反向回到 TUI。候选使用独立实例、会话和工作目录。守护自身不随日常 Agent 更新，首版不自动更新守护或迁移共享数据库。

当前首个提供商为 DeepSeek V4.1 Flash，官方 API 名 deepseek-flash，使用 https://api.deepseek.com/chat/completions。不使用 SDK；默认 non-thinking，启用 thinking 时保留 reasoning_content。依据 [DeepSeek 官方接入](https://api-docs.deepseek.com/) 和 [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode)。

实施的唯一执行清单见 [[openspec/changes/implement-agent-core/tasks]]；具体方案见 [[openspec/changes/implement-agent-core/design]]。最小 TUI 已按 [[openspec/changes/implement-minimal-tui/tasks]] 完成，核心与界面仍独立。

## 4. 最小 Agent 循环

### 4.1 外层交互与内层执行

外层处理连续用户输入。内层完成一个用户请求所需的多次模型与工具往返：

1. 保存用户输入，建立当前请求状态。
2. 构建输入：系统指令、工作目录、项目 AGENTS.md、Skill 目录、有效历史。
3. 必要时压缩已经完成的旧往返，给模型输出预留空间。
4. 调用模型并显示文本；完整保存模型协议要求的响应项。
5. 完整响应中包含工具调用时，验证名称与参数，按顺序执行并逐项保存结果，返回第 2 步。
6. 仅在模型正常结束且没有工具调用时，结束本次请求，返回用户。
7. 取消、网络失败、截断、协议错误均记录真实状态，不当成正常完成。

文本与工具调用可以同时出现。只显示了一段文字不意味着结束；未完整的流式参数不能执行。未知工具或无效参数反馈给模型。工具返回非零退出码也进入模型上下文，让模型决定后续动作。

### 4.2 Bash 与最小工具机制

首版只内置 Bash。参数包含 command、cwd、timeout；返回输出、退出码、耗时及取消或超时原因。每次调用独立非交互进程，不自动继承上次的 cd 或 export。取消和超时清理该调用的进程树。

工具接口使用普通名称映射：名称、描述、参数 schema、执行函数和取消信号。首版顺序执行，不实现并行工具调度。工具输出限长，完整输出落到本地会话产物文件，返回截断说明和路径。后台任务、PTY、交互式登录与持久 shell 暂不支持。

增量 I 不加入尚无管理进程可执行的管理工具。增量 II、III 增加管理接口时，Agent 的生命周期控制请求不是任意 Bash 命令文本解析出来的“暗号”。提供少量明确的控制操作：提交候选、运行候选验证、读取版本与验证状态、请求接替或回退。它们可以表现为固定的内置管理工具，由管理进程执行。普通文件操作仍由 Bash 完成。

### 4.3 Skill 和上下文

Skill 扫描项目 `.agents/skills/*/SKILL.md`，先提供名称、描述和路径，正文按需读取。没有 Skill 的项目也能完成普通编程任务。扫描不自动创建项目记忆目录、日志或工作流。配套脚本通过 Bash 使用。Skill 变更随实现版本保存；用户项目的 Skill 与 seeda 自身的 Skill 区分来源，不隐式写入自身版本。

压缩采用旧历史摘要加近期完整往返。保留目标、约束、已验证结果、关键文件、失败和未完成事项；原记录不覆盖。不能切开工具调用与对应结果。压缩失败保留原上下文并明确报告，避免清空历史或无限重试。

首版可在下一请求边界重新扫描 Skill，不提供正在执行中的热替换框架；核心更新统一通过新实例启动和主角色切换生效。

### 4.4 三类接口的最小职责

| 接口 | 输入与输出 | 首次实现阶段 |
| --- | --- | --- |
| 模型 | 接收有效上下文、可用工具和取消信号；输出文本事件、完整工具调用、结束原因与协议所需响应项 | 增量 I，只接入一种协议 |
| 工具 | 接收已验证参数与调用上下文；执行后返回结果、失败或取消状态；按 call id 回传 | 增量 I，首先只有 Bash |
| 管理 | 接收版本和实例标识、验证或切换请求；返回状态、证据位置和生命周期事件 | 增量 II、III，按具体操作实现 |

session/context 是普通内部模块，不提前抽象成记忆后端接口；Skill 是文件协议，不另设执行引擎。无需装饰器注册体系、事件总线、通用 hook 链或动态代码加载器。未来实际扩展需求出现时，可以修改这些模块或增加工具，仍然走版本验证流程。

## 5. Git、数据库与本地数据

### 5.1 三类内容分开保存

| 内容 | 存储位置 | 修改与恢复方式 |
| --- | --- | --- |
| 实现版本 | seeda 的 Git 仓库与版本目录 | Git 提交定位文件版本，启动对应目录 |
| 成长和运行元数据 | SQLite | 追加成长、验证和切换记录，事务更新当前选择 |
| 会话与验证产物 | 本地 JSONL 和文件 | 按会话写入，切换后继续读取 |

运行目录建议以一个本机数据根组织：`state.db`、`versions/`、`sessions/`、`evaluations/` 和管理进程日志。具体绝对路径实现前确定。它不位于某个运行版本内部，也不自动纳入 Git。

Git worktree 可以为同一仓库提供多个工作目录；每个工作目录有独立 HEAD 与索引，但共享仓库对象及部分管理数据。因此它用于版本并行，不是安全沙箱。[Git 官方文档](https://git-scm.com/docs/git-worktree)

### 5.2 实现版本的生成

A 从自己正在运行的已登记提交产生候选工作目录，只修改候选目录。候选实现、提示词、Skill 和依赖声明提交到 Git，再登记为 B。运行目录与候选编辑目录分开，已经启动的实例不接受原地源码修改。

B 以明确提交启动，依赖安装在独立环境中；不同版本不共享可被更新覆盖的依赖目录。锁文件与运行时要求随版本记录。不额外增加文件 Hash 或冻结 Contract；Git 提交、普通版本标识和现有依赖约束提供定位依据。

保留必要的 Git 引用使登记版本不会因历史整理而失去引用。首版不自动删除历史版本、验证证据或正在使用的目录。没有依赖版本约束时，只能恢复源码，不能声称完整恢复运行环境；实现应把依赖可恢复性纳入首版验收。

### 5.3 SQLite 最小逻辑模型

字段是职责草案，不是冻结的数据 Contract；代码实现按需要收敛。

| 表 | 核心字段 | 作用 |
| --- | --- | --- |
| versions | id、parent_id、git_commit、runtime_path、created_at、change_reason、runtime_requirements | 实现版本与父子关系 |
| evaluations | id、source_version_id、candidate_version_id、task、evidence_path、result、decision、reason、created_at | 验证结果与智能体评价；保留失败和取消 |
| instances | id、version_id、role、state、started_at、ended_at、failure_reason | 运行实例及退出记录；PID 仅为现场信息 |
| runtime_state | 单行 id、current_version_id、previous_version_id、phase、switch_from、switch_to | 当前主角色选择和未完成切换的恢复线索 |
| switches | id、from_version_id、to_version_id、requested_by、reason、state、started_at、completed_at、failure_reason | 接替、手动切换、故障回退的历史 |

评价结果与运行状态分开。B 可以正常存活却评价较差，也可以验证成功后在正式启动时崩溃。不要用一个 status 同时表示质量、版本、实例和切换状态。

数据库使用主键、外键、普通状态校验和事务。管理进程串行处理切换，只有一处能改变当前主角色。A、B 不直接并发写控制数据库。切换请求带 source_version 与 target_version，管理进程检查来源仍是当前主版本，拒绝旧实例延迟到达的接替请求。SQLite 同一时刻只有一个写事务，因此首版采用单写入者，不引入分布式协调。[SQLite 官方事务说明](https://www.sqlite.org/lang_transaction.html)

数据库保存证据路径和有界结论，不重复保存 Git 文件全文。凭据不写入版本、数据库、成长记录或会话配置；本地命令输出可能包含敏感内容，产物只能留在本机受限目录，不默认分享。

## 6. 守护进程与存活恢复

### 6.1 观察什么

- 子进程是否退出，退出是否为显式停服或正常交接。
- 启动阶段能否建立控制通道并报告 ready。
- 周期心跳与控制通道能否持续响应。
- 取消和退出请求能否在规定时间内处理。

ready 只表示实例已初始化、可以接收请求，不代表结果质量达标。心跳在模型等待与工具执行期间独立处理；耗时任务不能仅因没有文本输出被误杀。模型服务不可用、限流或任务测试失败，不自动等同本地 Agent 已宕机。

### 6.2 恢复策略

首次接替的新实例在启动阶段或接替后异常退出／持续失联时，停止该实例及所属工具进程，恢复上一个可用实现并记录失败。正常稳定运行的主实例发生异常时，首版允许一次有界的同版本重启；继续失败则回到 previous_version。具体心跳、启动期限与重试间隔在实测后确定。

失败版本不自动反复升级回来；原版本也无法启动时进入明确的不可用状态，CLI 报告故障并保留日志，避免无限重启和版本来回切换。用户主动退出或版本交接退出不触发回退。

数据库与产物目录本身损坏、磁盘不可写、宿主资源耗尽、模型服务故障等问题，不能保证靠切换代码修复。首版承诺在管理进程、存储和旧版本仍可用时恢复 Agent，不承诺零停机或恢复宿主全部服务。

### 6.3 守护进程的独立性边界

管理进程运行目录不随日常 Agent 版本切换改变；候选不能通过管理接口更新守护进程或迁移控制数据库。首版同一操作系统用户下的文件权限仍可能被 Bash 绕过，目录分离本身不构成强隔离。

因此首版面向可信本地自我修改任务，使用限定工作目录和管理接口维持工程边界，不宣称能抵御故意攻击管理层的候选。如果将来允许不可信生成代码拥有广泛执行权限，须另外设计进程用户、容器或文件系统权限隔离。此安全增强不隐含在 worktree 中，也不挤占当前实际功能验证。

## 7. A/B 并行验证

### 7.1 正常流程

1. A 在用户任务或自身运行记录中发现具体不足，提出有界改进目标。
2. A 在独立候选目录修改自身实现，形成 B 的 Git 提交，并通过管理接口登记父版本、理由与验证任务。
3. 管理进程启动 B，分配独立验证会话与测试工作目录。A 仍是主 Agent，可继续完成正式用户任务。
4. B 使用同一基础循环完成验证任务；保存文件产物、工具结果、失败和模型输出。
5. A 在自身串行任务的空闲边界读取证据并作评价。需要比较时，在等价独立任务副本上分别执行旧版与候选；不额外维护一套冻结 Baseline。
6. A 给出保持 A、接替 B 或继续修改的结论，记录范围、依据与不确定性。
7. 推荐接替时，A 发出明确请求，由管理进程执行主角色切换。

首版至少通过一个真实有用的自我修改场景验证整条流程。只用人工写好的 B 或伪造评价演示进程切换，不足以证明 RSI 闭环。

### 7.2 并行的限制

候选验证目录必须与用户工作目录分开。A、B 不共享可写会话、不同时修改同一用户文件。使用测试副本时，未提交文件如需参与验证，应复制进测试副本并注明输入；不能假定 Git worktree 包含原目录未提交修改。

涉及数据库、端口或外部服务的验证使用独立测试数据和临时入口；首版选择不依赖外部生产写入的任务。目录分离不隔离网络和凭据，B 默认不分配正式服务访问凭据；同用户 Bash 仍可能访问宿主凭据，这不是已实现的权限隔离保证。

“并行”指 A 保持正式服务、B 独立运行。A 的用户执行与候选评价仍串行，不新增同一主实例内多任务并发。首版同时只有一个候选；候选进行自我修改产生 C 的并行分叉延后，B 成为主角色后再创建下一候选。

## 8. 主智能体接替与版本切换

### 8.1 首版在请求边界交接

不迁移活跃 Bash 进程，也不让 B 重放 A 当前正在执行的命令。接替请求到来时：

1. 管理进程记录切换意图，暂停向 A 投递新的用户请求。忙碌时返回切换待处理；首版不建立复杂输入队列。
2. A 完成本次请求及全部工具往返，保存会话到持久目录并进入 idle。用户可先取消任务再切换；取消后的未知结果必须明确记录。
3. 管理进程要求 B 结束验证任务，关闭验证会话，并为正式服务启动一个新的 B 实例。这样候选任务历史不会混入用户会话。
4. 新 B 加载指定用户会话和兼容配置，完成 ready 响应；此时还不能执行用户任务。
5. 在一个 SQLite 事务中完成 current=A→B、previous=A 和切换成功记录；随后管理进程把新请求路由给 B。
6. A 收到退出请求，清理实例资源，退出进程。保留 A 版本、依赖与历史。

交接短暂暂停输入是首版允许的行为。先保证任务不重放、版本选择明确，不要求无感零停机。任意历史版本的手动选择也走同一路径；在兼容条件满足时复用已保留目录与依赖，不用原地 git reset 覆盖运行文件。

### 8.2 状态与崩溃恢复

最小切换状态为 requested、draining、starting、completed、failed；运行选择记录 switching 与 running 等阶段。SQLite 事务不能同时保证数据库写入、进程启动和消息投递的原子性；管理进程需按持久意图恢复，而不能假定三者一次成功。

| 故障时点 | 恢复行为 |
| --- | --- |
| B 验证失败或启动失败，尚未提交 current=B | A 保持主角色；切换失败，恢复接收输入 |
| A 尚未空闲 | 不切换，报告等待；取消或完成后再继续 |
| current=B 已提交但尚未投递请求，管理进程退出 | 重启读取当前选择，尝试启动 B；不可启动则恢复 A |
| current=B 已提交且 B 宕机 | 管理进程恢复 previous=A；加载会话时检查未完成工具记录 |
| 切换结束前 A 未按要求退出 | 先撤销 A 的请求路由，再终止所属进程；不把 A/B 同时作为主角色 |
| 管理进程重启，旧子进程残留 | 先核对控制通道并清理所属实例，再启动唯一主实例；不得仅凭数据库中的旧 PID 认领或杀进程 |

首版子进程在父控制管道关闭后停止执行并清理工具；管理进程恢复时仍需核对现场。当前主角色由管理进程实际路由与数据库选择共同确认，CLI 不能直接绕过管理进程向候选投递正式任务。

### 8.3 两类回退

存活回退由管理进程自动触发，无需模型判断；质量回退由当前智能体读取任务结果后请求，走同一版本切换流程。手动切换用于用户选择已登记版本。记录必须区分故障、质量、手动三类原因。

回退只恢复实现与运行选择，不撤销用户文件修改、已发出的网络请求或外部数据写入。需要恢复业务数据时，必须使用该业务已有的事务、备份或补偿流程，不把版本回退当成全局时间倒流。

## 9. 最小记忆与会话兼容

### 9.1 内置记忆只有 session

| 内容 | 保存原因 |
| --- | --- |
| 用户消息和完整模型响应 | 继续对话并保留模型协议所需信息 |
| 工具调用、结果与执行状态 | 理解实际动作，识别未完成或未知结果 |
| 压缩摘要和被保留的历史位置 | 从同一 session 重建下一次模型输入，不覆盖原记录 |
| 工作目录、请求和执行版本信息 | 重开或切换版本后知道任务环境和执行来源 |

首版一个 session 一份追加式 JSONL，当前实例是该用户会话的唯一写入者；候选使用自己的会话。加载时重建状态；尾部未写完记录不视为成功结果，保留现场并报告中断。文件中的历史消息不重新执行，只作为上下文。

不内置长期语义记忆、向量检索、自动知识抽取、项目图谱、Project Memory 显示器或专门的记忆数据库。SQLite 中的成长与运行记录属于版本管理数据，不承担通用记忆检索。

### 9.2 Project Memory 作为可选 Skill

仓库中存在 project-memory Skill 时，Agent 可按其说明读取项目背景与工作流，必要时通过 Bash 更新文件。若项目 AGENTS.md 明确要求使用，则遵循该项目规则；没有此系统也正常工作。核心不认识特定项目记忆的目录格式、不自动生成整套文档、不强制所有任务追加项目工作记录。

注意区分：本仓库已经使用 Project Memory 管理 seeda 的开发协作，这是开发规则；它不意味着未来 seeda 运行时必须把同一系统内置。

未来 Agent 可以基于实际收益提出更深集成，在候选版本中验证并决定是否内化；未经验证的需求不提前扩展首版。显示器可以以后独立读取同一批项目文件，不成为循环、启动或恢复依赖。

### 9.3 会话和版本兼容

用户会话独立于实现版本，以稳定的消息、调用和结果结构保存；每条记录关联请求和执行版本，调用使用原有工具 call id。需要时保存模型提供商要求的额外响应项，而不是仅保留可见文本。

工具启动前持久记录执行意图与 started，结束后保存 completed、failed、cancelled 或结果未知。进程崩溃在命令完成但结果未写入时，不能提供“恰好执行一次”的保证；恢复后保留 unknown，智能体检查现场并决定下一步。管理进程恢复服务不等于自动重跑未完成任务。

首版 B 必须能读取 A 的会话结构和控制接口，且不在候选更新中迁移共享 SQLite、改写旧会话或删除旧版本所需字段。这是首版支持自动回退的兼容范围，用普通类型、版本字段和兼容测试验证，不新增冻结 Contract。

改变共享数据格式、模型协议或守护接口的更新先留在后续人工管理流程，避免自动接替后旧版无法读取新数据。质量比较默认保持相同模型与关键参数；未来改变模型时记录差异，不能把模型变化和代码改进混成同一个结论。

## 10. 首版必须实现的部分

首版按三个连续增量建设；全部完成才称为本文定义的最小 RSI 系统。最小 CLI 可先独立验收，但不代表完整首版完成。

| 增量 | 必须实现 | 完成判据 |
| --- | --- | --- |
| I：可用 Coding CLI | 单模型、CLI、Bash 与工具调度、项目规则、Skill、会话保存加载、输出限长、压缩、取消与超时 | 真实编程任务能够读写文件、运行测试、修复失败并继续对话 |
| II：版本与存活恢复 | Git 版本登记、独立运行目录与依赖、SQLite、管理进程、ready／心跳、重启与 previous 回退、手动版本选择 | 新版不能启动或故障时旧版可恢复；版本和会话历史不丢失 |
| III：最小 RSI 接替 | 主 A 与候选 B 独立运行、候选任务、结果取回、A 评价、请求边界切换、失败记录与恢复 | A 实际生成一个有用改进 B，B 完成验证，A 请求接替；随后能回退 A |

### 首版不做

- 通用插件平台、市场、MCP 全套接入、多模型自动路由。
- 多候选竞争、多层自进化分叉、群体智能或进化任务调度器。
- 活跃命令迁移、正在执行的核心代码热替换、强制无停机切换。
- 守护进程自我更新、自动共享数据库迁移、全机服务回滚。
- 长期语义记忆、向量检索、自动知识提取、项目记忆数据库或显示器。
- 强制 Project Memory 初始化或把其专属文档结构写进核心。
- 首版 TUI 只包含输入、对话、工具状态和取消；复杂布局、主题体系、插件 UI 延后。
- 自动发布到外部系统。
- 在没有真实失败场景时增加自定义 Hash、冻结 Contract、Baseline 或开发 Gate。

## 11. 首版验收与故障演练

| 类别 | 实际场景 | 必须观察到的结果 |
| --- | --- | --- |
| 编程闭环 | 在临时项目中改函数、运行失败测试、再次修复 | 文件变化与测试结果实际发生，最终回答与证据一致 |
| 连续交互 | 追问前一请求及重开 CLI | 上下文可恢复，已完成命令不重复执行 |
| Skill 与压缩 | 调用带脚本的 Skill；小预算强制压缩 | 按需加载，压缩后能继续，工具往返对应完整 |
| 可选项目记忆 | 在无 project-memory 的临时项目完成任务；在有 Skill 的副本按说明使用 | 两者均正常；核心不强制创建项目文档或依赖显示器 |
| 取消与输出 | 长命令、超长输出、模型请求中取消 | 工具进程清理，输出可定位，CLI 可继续 |
| A/B 并行 | A 正式服务期间 B 在测试副本运行 | 用户文件与主会话无交叉修改，B 证据独立可读 |
| 自我改进 | A 改善一个可复现的问题，生成并运行 B | 修改来源、父版本、任务结果和评价理由完整；不是只有自我宣称 |
| 正常接替 | A 忙碌时请求切换，完成后接替 B | 等待边界，B 就绪后唯一主路由变化，A 退出 |
| 存活回退 | B 初始化失败、进程退出、控制通道失联 | 无模型参与也能重新启动 A，记录明确故障原因 |
| 手动与质量回退 | 用户选择 A；智能体因结果退化请求 A | 走同一切换机制，原因分开记录 |
| 切换中断 | 在启动前后、DB 提交前后终止管理进程 | 重启后恢复唯一主实例与确定版本，不留下双主路由 |
| 未知工具结果 | 命令产生副作用后，结果落盘前终止实例 | 恢复显示未知，不自动重放；智能体可核实现场 |
| 数据兼容 | B 写新会话后恢复 A | A 能读取允许范围内的数据并继续 |
| 依赖恢复 | 同一主机上切换已保留版本及环境 | 不因共享依赖被覆盖而破坏旧版启动 |

循环和状态转换可先用模拟模型检查，但模型表现、实际文件操作、进程退出、心跳、重启和 A/B 成长必须执行真实运行。故障演练在临时数据目录完成，保留失败记录；前置检查不能替代这些实测。

核心与接入已执行本地测试及真实 DeepSeek 编程样例；版本／守护／A/B 已完成本地故障演练及真实模型成长、接替与回退验证，见 [[docs/版本守护与RSI运行指南]]，具体证据与限制见 [[docs/Agent核心实现与验证]]。对“快速切换”的承诺先定义为复用已保留运行环境、无需重装依赖；实际耗时待测量，不预设毫秒级目标。

### 模块数量控制

增量 I 只需要 cli、agent、model、bash、session/context、skills 六个普通职责模块。工具调度可以留在 agent 内；无需为未来多个提供商拆出一套抽象类层次。源码文件按实际长度组织，不把“一模块一包”当成要求。

增量 II 加入 supervisor 与 version-store 等实际职责，复用 Git 和 SQLite；增量 III 通过管理接口增加候选启动、验证结果读取和切换请求，不另外造一套模型执行引擎。

### 测试与真实运行

用模拟模型验证工具调用对应、错误、停止、取消与压缩边界；用真实 Bash 验证副作用、退出和进程清理；用选定的真实模型完成实际编程任务。真实模型调用前明确凭据来源，不把凭据写进文档或日志。真实请求尚未发生时，只能报告逻辑检查，不能称为可用 coding agent。

### 自行实现与依赖边界

不引入 Pi SDK、Agents SDK、LangChain 等 Agent 框架；不使用模型 SDK 代管通信或循环。模型模块自行处理请求、SSE 分帧、响应事件、工具参数聚合、结束状态、失败与取消。session 的消息和必要协议项由本地代码保存。

TypeScript 运行时、编译工具、测试工具、SQLite 驱动或纯 TUI 渲染库不等同 Agent SDK，可以按真实需要采用；TUI 只负责呈现与输入，不拥有 Agent 循环或会话恢复逻辑。具体渲染库尚未选定，不把用户的 SDK 限制扩大成所有基础库禁用。

TUI 通过少量核心事件刷新界面：文本增量、工具开始／结束、请求结束／失败、版本变化。用户取消传给核心，核心再取消 HTTP 请求与工具。即使界面更新失败，也不将未完成工具标成完成。第二阶段保持同一事件形式，将核心调用改为管理进程通信。

## 16. 当前运行管理实现

第 4、5 部分及最小 A/B 接替已实现，源码在 src/versions 与 src/runtime。执行与验证清单为 [[openspec/changes/implement-managed-runtime/tasks]]，启动和故障恢复边界见 [[docs/版本守护与RSI运行指南]]。原架构中的单主、单候选、质量由 Agent 判断、共享 session、独立守护和请求边界切换均保留。

具体实现允许短暂停服：为避免两实例同时打开正式 session，先停止 A 再启动 B；B ready 后才提交当前选择。运行版本由专用本地 Git 库保留，不替用户工作树作初始提交。故障重试有界；没有后台操作系统自动启动配置，守护停服后重启会恢复已提交选择。npm start 默认自动初始化、后台启动或复用守护并接入前端；start:direct / SEEDA_MANAGED=0 保留直接模式。


## 16. 播种、种系与项目独立成长（2026-10-13）

seeda 的运行实例属于项目。每个项目选择一个初始实现播种，之后独立演进；经主动发布的完整实现可成为其他项目的起点。

| 术语 | 技术含义 |
|---|---|
| 种系 Strain | 可命名、选择、运行和传播的完整实现版本；内部继续使用版本 ID 和 Git commit |
| 播种 Seed | 选择种系初始化项目的初始实现与成长库 |
| 谱系 Lineage | 全局种系来源关系，以及项目内部 parent_id 版本链 |
| 嫁接 Graft | Agent 使用 Git/Bash，将其他种系的选定改进应用到目标候选并验证 |

### 全局种系库

默认 `~/.local/share/seeda/strains-library`，`SEEDA_LIBRARY` 可覆盖。Git 保存实现提交，SQLite `catalog.db` 保存唯一名称、ID、Git commit、实现目录、父种系、来源项目/版本和说明。`origin` 首次保存通用实现；以后更新通用入口不会改写它，项目可以主动发布其他起点。命名只用于发现，定位仍使用已有 Git commit 和 UUID，不引入额外 Hash 或契约。

项目主动 publish 一个已登记版本后，库从项目私有 Git 获取对应提交，保存可播种实现。发布以登记提交为准，不采纳运行目录未提交修改；会话、凭据、成长数据库与业务文件不进入全局库。名称重复拒绝，不覆盖旧种系。发布保存实现与来源，不等同目标项目质量验证，也不自动替换任何项目的主版本。

### 项目成长库

默认项目 `.seeda/runtime/`，保存独立 repository、versions、drafts、state.db、sessions、evaluations、outputs 和启动日志。项目 root 根据当前及祖先的已有运行库或最近 `.git` 定位，兼容 Git worktree 的 `.git` 文件；非 Git 项目首次使用 cwd。不同项目有独立守护、socket、版本选择与成长记录，能够同时运行。

SQLite 的 seed_origin 保存起始种系 ID、名称与 Git commit；后续 versions 保持项目自己的父版本链。播种将种系实现复制到项目私有 Git，独立安装依赖；全局库后来发生变化不影响已播种项目。初始化利用已有写事务，使来源与初始版本同时登记；已有实现拒绝重新播种，不覆盖历史。

### 通用接入

通用 `seeda` 入口支持 `strains`、`seed [种系名称或完整ID]`、`publish <新名称> [项目版本ID]` 和默认交互。未初始化时默认从 origin 播种；已初始化时直接运行项目自己的所选版本。前端和守护仍由通用入口启动，Agent 实现从项目保存版本执行。Agent 的 management 接口提供 strains 与 publish，成长传播也可由 Agent 调用。

SEEDA_HOME 保留显式运行根，用于已有运行库或特殊布局；不会自动搬迁、覆盖旧全局运行目录。旧共享运行模式被项目独立默认模式替代，详细操作与兼容办法见 [[docs/版本守护与RSI运行指南]]。嫁接的最终边界见下一节；种系删除/改名、跨机器同步、参数记忆迁移和自动传播策略仍未实现。


## 17. Agent 自主嫁接（2026-10-13）

用户最终选择以 Git 为基础，把 Graft 称为“嫁接”，由 Agent 自己完成；平台保持现有 Git/Bash、种系目录和候选管理接口，不引入专用导出/导入工具、插件体系或嫁接数据库。

Agent 明确源/基础种系及范围，以登记提交生成 Git 补丁，在目标当前版本的 draft 检查、应用并解决冲突。源种系和目标主版本保持保留，候选仍以目标版本为父，保留它原有改进。

检查后 submit，独立 evaluate，读取 evidence，记录 decide 后 promote；沿用已有质量接受和请求边界，不新增门禁。来源写入 submit reason，过程通过 Git、版本父链、会话工具记录和验证证据追溯。具体命令与边界见 [[docs/Agent嫁接流程]]。

补丁型嫁接允许代码适配，不等同即插即用；未来是否抽象统一功能接入接口根据实际需求另定。本轮不实现自动冲突解决或自动传播策略。

## 18. 种系发现与默认选择

全局 SQLite 设置表保存用户默认种系，介绍关联表保存 summary/improvements/scenarios/limitations/validation 五项文本。新发布必须提供，历史记录缺失则明确展示。来源/提交/时间自动保存，验证说明属于发布者声明，不自动构成质量认证。首次交互播种通过搜索选择器确认，非交互使用默认；已有项目不随默认变化。详细操作见 [[docs/种系选择与发布]]。

## 稳定安装层与 Agent 进化边界（2026-10-13）

CLI/TUI、守护、版本与种系管理属于稳定安装层；项目选择只切换worker执行实现。全局seeda不读取当前版本来启动版本内CLI。前端通过已有输入/取消/会话/事件接口连接稳定守护，切换后保持连接。

新种系只保存Agent实现与相关测试：core/model/tools、index、worker/protocol、Skill与包依赖；不保存cli、tui、版本/种系管理、守护代码或全局bin。旧完整快照可继续运行worker，下一次候选提交会收窄保存内容；不改写旧Git提交。前端/守护改进走独立安装更新，Agent promote不会替换它们。运行管理和前端仍同一包，不要求多包或新协议框架。
